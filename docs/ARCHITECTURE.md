# MonacoLabs.Presto — Architecture

A .NET animation library inspired by and initially ported from anime.js v4.5.0, with a framework-agnostic core and an Avalonia adapter. This document is the map: goals, the architecture, how it is tested, the project-wide decisions and the samples, with an appendix tracing each anime.js module to its Presto counterpart. What each feature does, and why, is in the [feature specs](specs/README.md); work not done yet is in the [backlog](BACKLOG.md); new work starts as a [change proposal](changes/README.md).

Provenance: https://github.com/juliangarnier/anime (tag `v4.5.0`, `src/` and `tests/suites/`). Docs: https://animejs.com/documentation.

## 1. Goals and non-goals

**Goals**

- anime.js-level ergonomics from C#: one call to animate any property of any object or control, with staggering, keyframes, timelines and full playback control.
- A timing model (delay, loop, loopDelay, alternate, reversed, seek, stretch, playbackRate, frameRate, composition) pinned by tests ported from upstream, so changes to it are deliberate and recorded as spec decisions.
- A core with zero UI dependencies that can drive plain objects (view models, custom renderers, game-style loops) and is fully testable with a manual clock.
- An Avalonia bridge that makes controls first-class targets: `AvaloniaProperty` by name or typed reference, transform shorthands (`X`, `Y`, `Rotate`, `Scale`…), colors and brushes, thickness, corner radius and points, with correct thread affinity and lifetime handling.

**Non-goals**

- CSS-specific value handling: unit conversion between px/em/rem, CSS variables, DOM attribute animation. Only what maps to Avalonia survives: numbers, degrees/turns/radians for rotation, percentages where Avalonia uses `RelativePoint`/`RelativeRect`.
- Three.js-style adapters. The adapter interface allows one; none ships.

## 2. Architecture

### 2.1 Core (`MonacoLabs.Presto`)

```
Clock                      framerate + playback-rate bookkeeping (base of Engine, Timer)
└─ Engine                  root clock, one per ticking thread; owns the linked list of running Tickables; Update(now)
└─ Timer                   delay/duration/loop/alternate/reverse state machine, callbacks, controls
   ├─ Animation            Timer + linked list of Tweens over resolved targets
   └─ Timeline             Timer + linked list of child Timers/Animations, labels, positions
Tween                      one (target, property) interpolation: from/to channels, ease, composition
Renderer                   static Tick(tickable, time, muteCallbacks, internalRender, tickMode) and Render()
IFrameSource               Start(Action tick) / Stop(); core ships ManualFrameSource (tests) and StopwatchFrameSource (headless)
ITargetAdapter             CanHandle(object) → IPropertyAccessor Resolve(object target, string property)
IPropertyAccessor          GetValue/SetValue on a target + IValueCodec describing how to tween the value
IValueCodec                Decode(object) → channels, Encode(channels) → object
```

This structure is what the ported regression tests exercise, and it ticks without allocating:

- **Linked lists** (`_head/_tail/_prev/_next`) for engine children, timeline children and tweens, for zero-allocation ticking.
- **`tick()`** turns absolute time into iteration time, handles loop/alternate/reverse/delay/loopDelay, fires callbacks and decides whether to render.
- **Composition** (`Replace` | `Overlap` | `Additive`) through a per (target, property) sibling registry; `Additive` sums onto running tweens through a per-engine additive pass.
- **Function-based values** wherever a number is accepted: `(target, index, total) => TweenValue`.
- **Time** is `double` milliseconds; seconds mode is an engine scale factor.
- **Threads**: one engine per thread that ticks it, no locks. `Presto.Engine` is the main (UI) engine and the ambient default; `Engine.Current`/`MakeCurrent()` install another for a block, and every `Timer` captures its engine at construction ([threading](specs/core/threading.md)).

### 2.2 Avalonia bridge (`MonacoLabs.Presto.Avalonia`)

- **Frame pump**: `AvaloniaFrameSource` re-requests `TopLevel.RequestAnimationFrame` each frame while the engine has children, falling back to a `DispatcherTimer` before any `TopLevel` exists; installed on first use. Minimized windows and backgrounded apps set `Engine.Hidden` ([initialization](specs/avalonia-bridge/initialization.md)).
- **Targets**: `AvaloniaObjectTargetAdapter` resolves typed `AvaloniaProperty` keys, names (including attached `"Canvas.Left"`) and the bridge's shorthands; writes go in at `BindingPriority.Animation`, so `Revert` clears them cleanly ([property-resolution](specs/avalonia-bridge/property-resolution.md)).
- **Shorthands**: transform (`X`, `Y`, `Rotate`, `Scale`…) composed into a bridge-owned `TransformGroup`; effects, 3D rotation, clips and masks over bridge-owned visuals ([transforms](specs/avalonia-bridge/transforms.md), [effects](specs/avalonia-bridge/effects.md)).
- **Codecs** for colors, brushes and gradients, box shadows, thickness, corner radius, points, sizes, rects, vectors, relative points, geometry and `GridLength` ([value-codecs](specs/avalonia-bridge/value-codecs.md)).
- **Render thread**: compositor animations for existing controls, and whole engines on the render thread in `CompositorScene` ([animation-thread](specs/avalonia-bridge/animation-thread.md), [compositor-scenes](specs/avalonia-bridge/compositor-scenes.md)).
- **Declarative layer**: `Presence`, `Motion`, `Follow`, `Animate.*`, recipes and markup extensions, and the controls built on them; see the [bridge spec index](specs/avalonia-bridge/index.md).

## 3. Testing strategy

- **Core**: xunit v3, no Avalonia. Tests drive `Engine.Update(now)` through `ManualFrameSource.Advance(ms)`, giving deterministic timing identical to how upstream tests use `engine.update()` and fake timers.
- **Regression suites ported from upstream**: `tests/suites/*.test.js`, with test names close to the Mocha `it()` descriptions so gaps are easy to audit. They pin the behavior Presto keeps; they are not the acceptance bar for new work. DOM-only suites (`waapi`, `threejs`, `node`, `build`) are skipped.
- **Generated fixtures** (provenance tooling): `tools/anime-fixtures/` (Node, `npm i animejs@4.5.0`) dumps JSON for easing curves (101 samples each), spring durations, stagger outputs and timeline positions; the C# tests assert within `1e-6`. Regenerate only when bumping the upstream reference version.
- **Bridge**: `tests/MonacoLabs.Presto.Avalonia.Tests` on `Avalonia.Headless` with `[AvaloniaFact]`/`[AvaloniaTheory]`. That package targets `xunit.v3.extensibility.core` 3.2.2, so `xunit.v3` is pinned to 3.2.x repo-wide (on 4.x, discovery throws `MissingMethodException`); it is also why `AssemblyInfo.cs` uses `CollectionBehavior(DisableTestParallelization = true)`. A `ManualFrameSource` replaces the frame pump.
- **Specs**: the feature specs are the acceptance reference. Each requirement cites the tests that pin it; `SpecTests` and `SpecCoverageTests` keep citations, paths and type ownership honest.
- **Visual**: the sample gallery is the manual acceptance surface; DevTools screenshots and property reads confirm end states.

Decisions behind the test setup:

- **Tests run on virtual time.** Headless tests freeze Avalonia's compositor clock and advance it through one test-only helper, `CompositorClock`, reached by reflection (each lookup throws naming a missing member; `CompositorClockTests` pins the seam). Tests step 16 ms frames and never sleep unless the code under test measures real time. The library itself keeps no reflection, and its own wall-clock reads go through a `TimeProvider`. Reason: Avalonia offers no clock seam, and real-time waits made the suites take minutes; the fragility of four private names is accepted because an upgrade that renames one fails loudly. Rejected: condition-based settles, elapsed-time pumps and shortened durations.
- **The bridge harness's `Tick(ms)` moves only the compositor clock.** It runs UI jobs, advances the compositor and renders, but does not advance the manual frame source; a test needing both engines in step advances both. The sample harness's `TestFrames.Tick()` moves both. Reason: advancing the frame source on every tick broke 35 tests whose UI-thread values assume `Tick` only renders.
- **The bridge test project uses the `MonacoLabs.Presto.Tests` namespace**, and its allocation tests are `BridgeAllocationTests`. Reason: a `MonacoLabs.Presto.Avalonia.Tests` namespace would reintroduce the `Avalonia.*` shadowing in the most Avalonia-heavy code, and the project already compiles the core tests' `EngineTestBase`, `TestHelpers` and `SpecCatalog` in that namespace; the rename keeps any test class name from existing in both projects.
- **Test assemblies run in series.** Reason: `Presto.Engine`, `Presto.Defaults` and the test frame source are process-wide statics. Rejected for now: per-test engines, which touch every static entry point.
- **`BridgeTestBase` tests must be `[AvaloniaFact]`**, and the base asserts it runs on the UI thread. Reason: a plain `[Fact]` reset the engine off the UI thread and caused order-dependent failures; the assert turns those into failures every time.
- **The sample suite's 60 s target is accepted as missed** (about 92 s). What remains is real rendering work in the headless framebuffer; tests were not weakened to reach it.

## 4. Project-wide decisions

- **Time is `double` milliseconds**; seconds mode is an engine scale factor, not a second code path. Reason: milliseconds are the unit every API takes and match `TimeSpan.TotalMilliseconds` and frame budgets (16.7 ms at 60 Hz).
- **Avalonia packages share the core's namespace.** The bridge's root namespace is `MonacoLabs.Presto`, and its package and assembly are `MonacoLabs.Presto.Avalonia`; its `Targets` and `Values` merge with the core's. Reason: an `Avalonia` namespace segment would shadow `Avalonia.*` for every qualified name and generated source inside it, and one `using` matches the API convention; separate assemblies contributing to one namespace is ordinary .NET practice (every `Microsoft.Extensions.*` package adds to `Microsoft.Extensions.DependencyInjection`). No core type shares a name with a bridge type in the merged namespaces, and no type is named like a sibling namespace. Rejected: a `MonacoLabs.Presto.Avalonia` namespace with `global::` at each qualified reference (the hazard stays for every future file and generator); `.Ava`/`.Xaml`/`.UI` (they read as workarounds, and `.UI` would not fit a second UI-framework adapter); merging the assemblies (the core would gain an Avalonia dependency).
- **Package names carry `Avalonia`; namespaces never do.** Lottie and DevTools are packaged as `MonacoLabs.Presto.Avalonia.Lottie`/`.DevTools`, with namespaces `MonacoLabs.Presto.Lottie`/`.DevTools`. Reason: on NuGet the package name is how people find the adapter for their UI framework; an adapter for another framework would be `MonacoLabs.Presto.<Framework>`, again in the `MonacoLabs.Presto` namespace.
- **Folders match the root namespace, not the project name.** In `MonacoLabs.Presto.Avalonia/`, `Controls/` holds `MonacoLabs.Presto.Controls`. Reason: the "folder structure equals namespace" convention is read relative to each project's `RootNamespace`.
- **Both packages target `net10.0` only.** Reason: the one blocker for older frameworks is `OrderedDictionary<TKey, TValue>` (.NET 9+); multi-targeting would mean carrying a hand-written replacement on a framework no test runs.
- **Code that needs nothing from Avalonia lives in the core.** A bridge type whose implementation uses only core types moves to the core, unless a bridge feature defines its meaning (as Recipes defines `MotionTokens`, or compositor layout transitions define `LayoutMotion`). Reason: core users get it, its tests run without a headless platform, and `using MonacoLabs.Presto;` reaches it.
- **Every trigger, recipe and control states its reduced-motion form** in its spec, and its tests run under both settings. Reason: four places once ignored `ReducedMotion` and samples worked around them; stating the reduced form up front stops new holes.
- The architecture rules (the core knows nothing about Avalonia, single-threaded engines, a timing model changed only deliberately) are in [CLAUDE.md](../CLAUDE.md).

## 5. Samples

Two samples dogfood the library: the gallery, one page per feature, and Tempo, one app built with it. No spec owns sample code, so their decisions live here. One rule covers both:

- **Demos never quietly grow the library.** Every friction point a sample hits is recorded as a finding and decided on its own; generally useful sample code is a candidate for the bridge rather than a quiet copy in the sample.

### Gallery

The gallery (`samples/PrestoSample*`) is the dogfooding surface and the manual acceptance target. The gallery's decisions:
- **Reference pages stay isolated; multi-feature demos are separate.** The Reference section (`Pages/`) keeps one page per Presto feature, ordered by the spec areas (timing, animation and values, timeline, stagger, eases, then the bridge), in the dictionary/indexer form with string keys, so the params API sits next to its builder twin; a page with a twin shows that API's raw behavior and ignores the reduced-motion switch, and the twin shows the reduced-motion-aware form. Showcase (`Showcase/Pages/`) holds the multi-feature demos; Builder pages use only the builder, never the params indexer, and existing Reference and Showcase pages were not converted to it.
- **Printed code is the code that ran**, captured at compile time (`Snippet.Of`, and the `PrestoSample.SnippetGenerator` regions), never a hand-copied string. Reason: copies drift silently.
- **The nav is one `TreeView` of sections, in one `GalleryNav`.** Reason: two `ListBox`es bound to one `SelectedItem` fight, the one not containing the selection writing `null` back.
- **The shell is adaptive at a 720 DIP width breakpoint.** At 720 and wider it keeps the sidebar master-detail; narrower it is a two-level stack, Home (the nav at full width) and Page (top bar with back button and an About toggle). Width decides, not platform. Reason: desktop is the acceptance target and jumping between pages from an always-visible list is fastest there, while the Browser head runs on phones and desktops, tablets rotate, and a width rule is testable on Desktop (`--size 400x850`) and headlessly; 720 is the 240 px sidebar plus the narrowest content column (~480) that still reads as a page, so portrait tablets keep the sidebar. Rejected: page-based navigation at every width; `OperatingSystem.IsAndroid()`-style checks; container-query styles alone, which can restyle but not move the nav.
- **One `GalleryNav` is moved between the sidebar and Home**, only when the layout changes. Reason: a second nav would fight over the selection, and one instance keeps search and expansion state across a layout switch.
- **`MainViewModel` owns navigation** (the back stack, `AtHome`, `IsCompact`); the shell drives the transitions from it. Reason: one source of truth for both layouts and the headless tests. Rejected: Avalonia's `NavigationPage`, whose own stack and back button would have to be kept in step and which cannot host the wide layout.
- **Home and Page stay attached, and `PrestoPageTransition.Start` (`PagePush`) is called on them directly.** Reason: a `TransitioningContentControl` swapping Home out would detach the nav, losing its scroll position and replaying its entrance on every back.
- **Overlays get the back request first.** The shell re-adds its `TopLevel.BackRequested` handler each time a page loads, so it runs after the handlers of the overlays that page attached; at Home the request is left unhandled so the OS can close or background the app. Reason: `Dismissal` subscribes in registration order and the shell subscribes first, so back would otherwise leave a page with its sheet still open (BRIDGE-SHEET in the backlog).
- **Back is Alt+Left and the mouse back button, not Escape**, and the wide layout has no back button. Reason: Escape already clears the search box and closes overlays; the desktop look stays unchanged and the sidebar is always one click away. Rejected: a header back button shown while history exists. In compact, Avalonia turns Alt+Left and the mouse back button into `BackRequested` before the page sees the key, so each press pops one level but the Board's Alt+Left reorder is lost there; accepted, since compact is touch-first and the list still reorders by drag.
- **Twin links push; nav choices replace in compact**, so back from a page chosen at Home goes Home, while a twin link is a detour you return from. The wide history is capped at 50 pages.
- **One dark look, by setter values only.** Shared classes keep their names and roles and only setter values change, so no reference page is edited; colors come once from `Showcase/Palette.cs`, because compositor scenes cannot read `StaticResource`. The library stays theme-agnostic.
- **The reduced-motion switch sets `ReducedMotion` only**, not `ReduceAll`.
- **Showcase pages share a kit**: `ShowcasePage` owns a `ControlScope` reverted on detach, and data comes from seeded `Datasets`, so every run looks the same.
- **Page patterns stay page code where no library primitive fits.** Liquid's squashing pill and the Swipe deck's card throw stay in the pages; Dashboard's donut and sparkline, Loaders' ring and counter, MorphLab's signature and TitleSequence's monogram stay off the draw recipes. Reason: Liquid's edges lead and trail on different durations and squash vertically, which `Stretch` cannot express; the deck is a card throw, not a row action; the draw cases are not direct swaps (scrubbable timelines, keyframe loops, a `ProgressBar`, a timeline the reduced form would shorten).
- **The Animatable reference page stays hand-built**, and the `Magnetic` demo lives on the Micro-interactions page. Reason: that page demonstrates `Animatable.Set` itself; its follower also maps the pointer to stage coordinates and holds on leave, which is neither proximity nor the pointer sources' absent-reads-0 rule.
- **GalleryFlip stays imperative**, the `AnimateLayout` counterpart to Storefront. Reason: converting it to `Presence` would make it a near-copy of Storefront's grid.
- **The Photo viewer is its own Showcase page** (pinch, bounds, 90° snap, double-tap, Ctrl+wheel, a filmstrip `Carousel`), linked from the Draggable page, not a fifth Gestures tile. Reason: the Gestures page's first row of four tiles is full at its width; on desktop the `Carousel` swipes on touch and pen only, so photos change through the filmstrip.
- **The Gestures drag-to-open card is a second, full-width row**, not a narrower fifth column. Reason: its staggered rows need a wider card than a quarter column gives, and a fifth column would squeeze the first four tiles.
- **The Gestures trails and resist demo is a third full-width row**, below the drag-to-open card. Reason: a pointer trail needs a wide stage to read as a trail, and the first row's four tiles are full at the page's width.
- **Image effects demos.** The duotone card flips a `ThemeVariantScope` (the app is fixed to Dark); Storefront's product art is a `DrawingImage` in a `FilteredImage`, grayed when sold out by a style setter, exercising rasterization; the hero dissolve is the Photo viewer's dimmed `FilteredImage` backdrop; the dissolve/pixelate card animates the live image, then removes it. Reason: the Connected and Gallery flip heroes hold no image, and exit ghosts cannot carry pixel effects.
- **The carousel snaps through the draggable's `Snap`** (as `ModifyTarget`) and marks the active dot in `OnSettle`. Reason: `OnSnap` fires at release, before the inertia lands.
- **Storefront skips its cart-badge burst under reduced motion**, since the badge's own `Pop` covers it; the Micro-interactions like passes `Recipes.Fade()` as its reduced form and bursts when the heart turns on, not on press-in.
- **The Activity feed inserts live events at once**, even scrolled down, counting unseen ones in an "N new above" pill that scrolls to the top. Reason: scroll anchoring makes holding events behind the pill unnecessary. Its one-off 39 px offset was closed as not reproduced (selection, focus and the FLIP ruled out; anchoring cannot engage at offset 0), with `ActivityFeedPageTests` kept as regressions. Those tests seed the feed from 18:00 because seeding from `DateTime.Now` made the live timer's phase vary with the time of day.
- **Desktop is the acceptance target.** Scene-heavy pages cap their counts and degrade on Browser; other heads are checked once and the README's Platforms table states only what is true. `PrestoSample.Tests` constructs, attaches, ticks and detaches every page headlessly in both motion modes, because DevTools input cannot send pointer moves or drags.

### Tempo

Tempo (`samples/Tempo/`, usage in its [README](../samples/Tempo/README.md)) is a Pomodoro focus timer with a task list, built the way an outside consumer would build an app with Presto. Its friction points are the "Tempo findings" in [BACKLOG.md](BACKLOG.md). Its decisions:

- **Standalone, not a gallery page.** It references only the library packages, never `PrestoSample` or its kit, and has its own palette and styles. Reason: it should read as an app someone built *with* Presto, copyable as a whole. Rejected: a Showcase page, which would inherit the kit and the shell's constraints.
- **One Desktop head, responsive by width.** One WinExe project with no shared/heads split, whose layout works from 320 DIP up, with a compact arrangement below 720. Reason: desktop is the acceptance target and a focus timer is a desktop app, while a width rule is testable on Desktop (`--size 360x780`) and headlessly, so a narrow window works without a phone head. Mobile and Browser heads are out of scope; the split can come later if one is wanted.
- **One shell, two arrangements.** `ShellView` sets a `compact` class and `MainViewModel.IsCompact` from its width in `MeasureOverride` (so the first frame already has the right layout), and only when the side changes. Below the breakpoint the title bar keeps only the wordmark, and the Tasks column, the Focus | Stats switch and the gear give way to a bottom bar of Tasks, Focus and Stats (a `Selection.Indicator` pill, and the chosen icon pops through a `Motion.State` setter on `:selected`) with a Settings button beside them, and a third `AppView.Tasks` page adopts the one `TasksPane`, which returns to its column when the page leaves; Tasks maps to Focus when the window widens, and the page and selection survive the crossing. Everything else is style selectors on `compact`: the Focus dial sized to `min(300, width − 48)` and to the height the mode label, controls and summary leave, with the digits scaled in a `Viewbox`, the tag chips scrolling sideways, the Stats cards in one column. The breakpoint is 720 DIP, as the gallery's. Reason: the gallery's rule that width decides, not platform, and one view model for both layouts, so the tests drive both. Rejected: container-query styles alone (they restyle but cannot move the task list between a column and a page), and two separate shells (the state would be duplicated).
- **Compact moves side surfaces to the bottom.** Task details open in a bottom `Sheet` with detents at half and full height, and settings in a bottom `Sheet` with the same rows and stagger; the confirm dialog stays a `Modal`, and the toasts sit above the bar. One `TaskDetail` and one `SettingsFlyout` move between the wide and compact hosts (`ShellView.PlaceSurfaces`), only the live detail surface binds `IsDetailOpen`, so an open detail moves across the breakpoint, and open settings close. Reason: a 320 px screen has no room for a side drawer or an anchored popover, and a bottom sheet is the phone convention (and shows off `SheetDetents`).
- **The drawer and sheets settle with a `TimeConstant` of 150 ms**, not `Sheet`'s default 350. Reason: at 350 the details drawer took about a second to come to rest; at 150 it settles in roughly 400 ms and a fling still travels (BRIDGE-SHEET).
- **Semi.Avalonia (Dark), not Fluent.** Semi supplies the base controls, flyout and inputs; Tempo's styles restyle the hero surfaces over Semi's color tokens and clear theme transitions on properties Presto animates. Reason: every gallery page runs on Fluent, so a feature quietly coupled to Fluent's templates would go unnoticed. Rejected: Fluent (tests nothing new) and the Simple theme with hand-styled controls (no third-party-theme coverage).
- **The intro is built with Presto, not Lottie.** Reason: it shows the library doing what the app does (draw, particles, a motion path, OKLCH color, connected flights) and needs no licensed asset; a canned clip could not hand its elements off.
- **The intro becomes the app.** Its ring and wordmark carry the `Connected.Key`s of the Focus ring and the title-bar wordmark, so swapping `IntroView` for `ShellView` flies them into place, while the shell's other parts fade in alongside through a `handoff` class (`Connected.Anchor` plus `TempoMotion.HandoffFade`). Reason: a splash that fades out before a UI fades in reads as two things. Rejected: a splash window (no flight across windows) and one `Presence.Enter` fade on the shell, which would fade the flights with it. The ring's key is cleared on the first page swap, or every Stats → Focus return would fly the ring again and replay the anchored fades. The flight on the first swap, onto a never-measured shell, lands on its target, so the planned fallback of attaching the shell hidden first was not needed.
- **The intro is a code-built timeline.** `TempoIntro` lays `TempoMotion` builders out on one `Timeline` by position (about 2.3 s, then the flight), and `IntroView` starts it on attach. Reason: overlaps, a skip (`Complete()`) and an awaited end are what timelines are for, and XAML has no timeline spelling by design. `Recipes.Assemble` starts from a timeline callback, and a skip cancels it and sets the wordmark's landed state, since a particle effect cannot join the timeline.
- **The intro only adds a minimum duration.** The real load runs underneath and the handoff waits for both; a click, Space, Enter or Esc skips it, a setting and `--skip-intro` turn it off, and reduced it is the ring and wordmark fading in over about 400 ms. Reason: a fake wait that cannot be skipped is the opposite of premium.
- **XAML owns the tree; `TempoMotion` owns the motion.** Every animation is a `public static readonly AnimationBuilder` in `Motion/TempoMotion.cs`, each with a `WhenReduced` form, assigned from XAML with `{x:Static}`, or a `{presto:…}` recipe extension where one says it exactly. Code-behind only triggers a builder where no XAML trigger exists, never builds one inline. Reason: one place to read and tune all the motion, and a whole-app test of builders as the value lifecycle surfaces carry (CORE-BUILDER). The tick dot's path builder is a method, since a motion path is read from a laid-out shape.
- **The code-only exceptions are explicit**: particle effects (`Recipes.Burst` on session complete, `Recipes.Assemble` in the intro), the per-block glyph morphs of the countdown and the start/pause label (`Recipes.MorphGlyphs` on each `RemainingText` and `StartPauseLabel` change in `FocusView`), the Focus dial's size from the page's width and height (`FocusView`), the hold-to-abandon shake on an early release (`FocusView`), the compact arrangement from the width, the Tasks page adopting the one `TasksPane`, and moving the detail and settings between the drawer and popover and the bottom sheets (`ShellView`), opening the settings flyout or sheet from `OpenSettingsCommand` and the settings button's open class, opening the confirm dialog from its button and the clear's sequence (`ShellView`), the dialog's Escape shake (`ConfirmDialog`), the stepper value morphs (`Stepper`), scrolling an added task into view (`PrestoAvalonia.ScrollToIndex` with `Nearest` on `MainViewModel.TaskAdded`, in `TasksView`), replaying the motion preview on a setting change (`SettingsFlyout`), showing a toast (`ToastHost.Show`), the reduced-motion flag (`App.ApplyMotionSetting`), the intro timeline and the backdrop drift (`AnimateOnCompositor` in `ShellView`). Each is a call in code-behind reacting to a view-model event or an attach, and each is a backlog finding. Reason: the rule is to prefer XAML, not to bend the app around it. Rejected: app-side attached properties wrapping them, which would be the library growing quietly inside a sample.
- **Each digit is its own block; the totals flip.** The countdown is a row of `TextBlock`s, one per character of `RemainingText` (`FocusView.ShowRemaining`): each digit sits in a fixed 36 DIP slot with its glyph centered, since Inter's figures are proportional, and the colon's block never changes. On a tick only the blocks whose character changed morph (`Recipes.MorphGlyphs`, one running morph per block), as `RollDigits` rolls only the changed columns (BRIDGE-RECIPES-062). The row is rebuilt when the text's length changes, so a 120-minute session's `120:00` gets a third minute block. `FocusView` watches the view model only while loaded and completes every running morph when it unloads; the Stats totals keep `SplitFlap`. Reason: morphing the whole block split and unsplit every glyph each second, which redrew the unchanged digits as unhinted outlines and hopped the colon (BACKLOG, BRIDGE-RECIPES), and a block that never morphs cannot move; per-block morphs also make "only what changed animates" true, and keeping `SplitFlap` on the totals shows both effects. Outcome of the "`MorphGlyphs` once a second for 25 minutes" question: each call completes the last morph, which releases its split, width hold and overlay host, so nothing accumulates across a session; the per-call cost that remains is a backlog finding (BRIDGE-RECIPES). Rejected: Inter's tabular figures (the glyph recipes' splits and outlines take no font features), switching the clock to `RollDigits` (the morph is the showcase effect; it stays an option if a per-digit morph still swaps visibly when it ends), and fixing `MorphGlyphs` in the library alongside (a library behavior change with its own spec decisions, so it is logged instead).
- **Reduced is no animation for changing values.** Under `Presto.Defaults.ReducedMotion` the countdown, the start/pause label and the settings steppers write `Text` directly, with no morph or crossfade. Reason: a value that changes every second must not blink; reduced motion means less motion, and `MorphGlyphs`' reduced crossfade each second is more distraction, not less. Other reduced forms are unchanged.
- **The last ten seconds pulse the ring.** `FocusViewModel.IsFinalCountdown` (running, `00:10` to `00:01`) puts a `final` class on the ring, whose style sets `Animate.OnChanged` to `TempoMotion.FinalPulse` while the ring's `Animate.Watch` follows `RemainingText`, so each second's change plays a glow in the ring's own color (reduced: an opacity blink). The view model sets the flag before the text, so `00:10` pulses and the segment end, where `00:01` morphs into the next segment's time, does not. Reason: a declarative trigger, with no per-second token beyond the text that already changes.
- **Start/pause is a pill that becomes a circle.** Idle it reads "Start focus" or "Start break", paused "Resume" (`FocusViewModel.StartPauseLabel`, set on every refresh, since paused and idle both read `IsRunning` false); running the label hides and only the pause icon shows. Starting turns the play triangle into the pause bars with a half-turn and a small pop (`IconToPause`; the bars are the same upside down, so the turn lands square, and pausing turns it back), and an accent halo behind the pill pings outward (`StartHalo`, `StartPing` as a `Running` state whose held end is invisible, so leaving the state shows nothing). The accent pill is a `Border` host with `Animate.ContentSize` (`TempoMotion.PillResize`), sized by a transparent `Button` inside it: 20 px padding either side of the 24 px icon makes the 64 px circle. The corner radius is a constant 32, half the fixed height, so it is a pill at every width. A label replacing a label morphs (`MorphGlyphs`, set at once under reduced motion); one appearing or hiding is set at once and revealed or clipped by the resize. Reason: a content size host lays its child out at the final size, so an accent drawn by the `Button`'s own presenter jumped to the new width while only the clip eased; the `Border`'s own background eases. Lift and PressIn move with the pill, the Ripple stays on the button.
- **The Focus view centers by hand where a stack would not.** The digits sit alone at the dial's center, and the task title hangs below them under a top margin, so the digits stay centered whether or not a task is active; the mode label's `TransitioningContentControl` stretches the full width and centers each label in it. Reason: a centered stack of digits and an empty title put the digits 12 px high, and a content-sized label control took the wider label's width mid-swap and left-aligned the other until it settled.
- **The small buttons are states.** Skip and stop are a matched pair of 40 px circles: a glass disc (`Ellipse.disc`, lit on hover by `DiscLight`) inside the same faint track. Hovering skip opens its glyph into a fast-forward (`SkipToForward`, a `MorphTo` onto two triangles sharing the glyph's bounds, so the icon keeps its size). Skip's tooltip says where it goes ("Skip to break"/"Skip to focus", `FocusViewModel.SkipLabel`), and every tooltip opens and closes through `Popover.Open`/`Close` (`TipOpen`/`TipClose`, quicker forms of the settings popover's). A skip fast-forwards the glyph out and back in (`SkipForward`) while a sweep runs once round its ring (`SkipSweep`, a `Draw`), echoing the stop button's hold, played from `Click` since `Animate.OnTapped` plays on the tapped element only. A confirmed abandon crosses the stop square out and back (`AbandonCross`, a `MorphTo` keyframe pair on a cross sharing the square's bounds) as the full ring collapses inward and returns once it has rewound (`AbandonCollapse`). The settings button turns a quarter (`GearSpin`) on hover and through an `open` class that `ShellView` sets from the flyout's `Opened`/`Closed`; the add box's plus (`TextBox.InnerRightContent`, a button running `AddTaskCommand`) morphs into a check with a full turn while `MainViewModel.HasNewTaskText` (a `ready` class), so the check lands upright. Reduced, the turns and the sweep do nothing, the tooltips open and close at once, the skip, cross and collapse blink, and the plus morphs at once (`Duration(1)`, BRIDGE-MOTION). The plus's state is in XAML: the tasks view attaches once, with an empty box.
- **Magnetism is ambient, plus the two loose icon buttons.** The four backdrop blobs lean towards the pointer at different strengths (0.12-0.25, so they part like layers), with a 240 DIP reach and a slow `"0,1400"` `Magnetic.Spring`, on the blob inside each drifting slot so the compositor drift and the pull never contend for one transform; and as the pointer nears a blob's center (`PointerProximityValue` from the center over 520 DIPs, through the same spring) it grows up to 15% and brightens from 80% to full opacity (`ShellView.Swell`, `TempoMotion.BlobSwell`/`BlobGlow`). The settings gear and the add box's plus reach a little for the pointer (0.3 and 0.25 over about 28 DIPs). Reason: on the start pill the pull fought its hover lift and read as the button running from the cursor, and on skip and stop, side by side in one row, it read as the controls wobbling; a backdrop that follows the pointer shows the effect without moving anything the user aims at, and a lean alone was too subtle to notice behind the panels. A touch screen sees none of it, as the pull follows a mouse.
- **Space is the timer's key wherever focus is.** `MainWindow` handles Space on the tunnel (down and up), so it starts and pauses even with a button focused, except in a `TextBox` and on a hold ring, which keep their own Space. Reason: as a window key binding it ran and then the focused button clicked too, so after clicking Start the timer toggled twice, and after clicking Skip it skipped. Rejected: unfocusable buttons, which would shut out keyboard users.
- **Settings stays a popover or a bottom sheet, not a page.** Wide it is a popover under the gear; compact it is a bottom sheet with the same rows (above). Reason: it is about ten controls, used rarely and briefly. A page would be mostly empty, would swap the Focus view out (and with it the running ring), and would make the page switch mix content with configuration; a popover or sheet keeps the timer in view while durations change, and is where the Popups page's stagger reads best. Compact opens it from a Settings button at the end of the bottom bar, not the title bar: a phone's top corner is out of thumb reach, and the title bar's top edge sits under a phone's status bar. It is a button beside the page `ListBox`, not a fourth item, so it opens the sheet over the current page and the pill stays on that page. Rejected: a page in the switch or the bottom bar, a fourth `AppView`, and a right-edge `Drawer` (the task details already use one).
- **The settings panel is a glass presenter over one flat list of rows.** The flyout's `FlyoutPresenterClasses="glass"` restyles Semi's presenter (translucent fill at 90%, more opaque than the panels since a popup may sit over busy rows, the top-lit edge, 14 px corners), and its four sections (Timer, Behavior, Motion, Data) are headings among the rows of one `StackPanel`, whose children arrive with `TempoMotion.SettingsRowArrive` (rise and fade, 25 ms apart, a beat after the presenter's `FlyoutOpen`; reduced, a fade all at once). Closing plays `FlyoutClose` (`Recipes.PopoverOut`, the reverse of the open) on the presenter, and the rows leave with it; reduced, the popover closes at once (BRIDGE-POPOVER-026). Reason: an arrival batch is keyed by the nearest `Panel` (BRIDGE-PRESENCE-020), so nested section panels would each stagger from 0; and the content unloads with the popup, so its own `Presence.Exit` never plays. The Behavior switches sit right of a caption like the steppers, with Semi's header and On/Off text cleared.
- **Steppers replace `NumericUpDown`.** `Views/Stepper` is − / value / + over two `RepeatButton`s (holding one repeats, Tab and Space reach both, `{presto:PressIn}` on each), with `Value` and `Maximum` styled properties; a step clamps to 1 and the maximum (1–120, 1–60, 1–60, 1–12) and the buttons stay enabled at a limit, so keyboard focus never drops. The value morphs with `MorphGlyphs` from the stepper's code-behind while loaded, in a fixed, left-aligned box, and is set directly while the settings are closed or under reduced motion. Reason: a one-property control is the smallest reusable piece, and a disabled button at a limit would throw focus out of the popover.
- **The motion setting previews itself.** A dot beside the System / Full / Reduced switch plays `TempoMotion.MotionPreview` from `Animate.OnAttached`: a looping bounce, or reduced one fade in, since reduced loops stop. Closing the popover detaches its content, which reverts the loop (BRIDGE-ATTACH-003), so nothing runs while it is closed. `SettingsFlyout` replays it on each `Motion` change, after `App.ApplyMotionSetting` has written the flag, since the reduced form is resolved when it starts; System shows whichever the OS flag makes effective. Reason: the choice is abstract until it moves something.
- **Clear and restore confirm in a `Modal`, not a page or a second drawer.** `ShellView` hosts a `presto:Modal` over the whole shell (title bar included, `ZIndex` 2) with `Views/ConfirmDialog` as its content, `IsOpen` bound two-way to `MainViewModel.IsConfirmOpen` and the panels grid as its `Backdrop`, so they blur. Reason: the modal gives the circle reveal from the pressed button and the backdrop blur a page could not, and the task details already use the right-edge drawer wide and a bottom sheet compact (two surfaces on one edge confuse). It stays a `Modal` in compact too. Rejected: a page in the switch, a second `Drawer` or `Sheet`.
- **The settings popover closes before the dialog opens.** `RequestClearCommand`/`RequestRestoreCommand` set `ConfirmAction` and raise `ConfirmRequested`; `ShellView` takes the pressed button's center, hides the flyout (or closes the settings sheet) and calls `Modal.Open(point)`. Reason: on desktop the flyout is its own popup window, drawn above the modal's scrim, and `Open(from)` finds no origin for an element under another visual root (BRIDGE-MODAL-004), so the center goes through `PointToScreen`/`PointToClient`. Without the button on screen (a command run with settings closed) the dialog opens without an origin, at once. Under reduced motion the content shows at once and only the scrim fades (BRIDGE-MODAL-022); Tempo adds no form of its own.
- **Both actions are held, not clicked.** The dialog's red button is a `ProgressRing` (`HoldDuration` 600, `SemiColorDanger`) around a drawn red face, and its `Confirmed` runs `ConfirmCommand`; Cancel, a scrim tap and Escape close as cancel. Once the ring has moved (`Value` above 0, by pointer or Space/Enter), Escape shakes the card (`TempoMotion.DialogShake`, `Recipes.Shake`; reduced, an opacity blink) instead: `ConfirmDialog` handles the `KeyDown` before `Dismissal`'s top-level handler sees it, and `ConfirmDialog.Reset` forgets the press at each opening. Reason: restore replaces data as surely as clear, and a started hold means the user meant something, so a stray Escape should not silently drop it.
- **The clear is a sequence the view plays before the view model clears.** `ConfirmCommand` awaits `PlayClear`, which `ShellView` sets and which calls `MainViewModel.ClearAll` at its end: the visible rows scatter (`TempoMotion.ClearScatter`, `Recipes.Scatter` with a fixed seed and the order stagger; reduced, a fade), then the Stats bars drop to their baseline in turn if Stats is showing (`BarCollapse`; reduced, a fade), then the clear runs and the empty list's `WordFade` line arrives with `Tasks.Count` at 0. The scatter is reverted only after the clear: the removed rows' `Presence.Exit` ghosts snapshot them already scattered (so nothing flashes back), and their recycled containers must come back whole for a restore. Restore needs nothing of its own: `Replace` removes and re-adds the rows, which leave with `RowExit` and arrive with `RowEnter`'s stagger. Reason: switching the rows' `Presence.Exit` to a scatter would play it with the removal, in the same pass as the empty line and the bars' replacement, so nothing could come between. Without a `PlayClear` (no view) the clear applies at once.
- **Abandon shakes when let go early.** The ring has no early-release event, so `FocusView` handles its `PointerCaptureLost` and Space/Enter `KeyUp` and plays `TempoMotion.AbandonShake` (`Recipes.Shake(.6)`, an opacity blink reduced) on the ring and its icon unless the hold confirmed. Reason: a release that does nothing reads as broken.
- **Wall-clock time is the truth; Presto only presents it.** `FocusClock` derives elapsed, remaining and progress from a `TimeProvider` on every read, a 4 Hz `DispatcherTimer` refreshes the view model, and the ring smooths between updates with `Follow`. Reason: the bridge pauses the engine while the window is minimized (BRIDGE-INIT), and a focus timer must keep counting; a `TimeProvider` also makes the clock testable. Rejected: a Presto `Timer` as the session clock.
- **The mode is the root's `Motion.State`.** The shell binds `FocusViewModel.MotionState` (the mode, plus `Running` while the clock runs, since a state takes one value), and the accents (the backdrop gradient's among them, an `accent-bg` border under a fading `OpacityMask`, since a gradient stop is not a control a state can target) are `MotionStates` in shared styles that descendants follow, staggered by `StaggerChildren`, recoloring through OKLCH. Reason: one binding drives the whole window's mode change, and OKLCH keeps coral to aqua from passing through gray.
- **The backdrop drifts on the compositor.** Four soft blobs (`accent-bg` borders under a radial `OpacityMask`, so they recolor with the mode like the backdrop gradient) drift on 21–39 s alternating loops, one `TempoMotion.BlobDrift` builder giving each blob its own offset, scale and period through function values. `ShellView` starts it with `AnimateOnCompositor` on load, reverts it on unload, and restarts it when the motion setting changes, since the reduced form (no properties, no loop) is resolved at start. Reason: an ambient loop that runs all day must cost no UI-thread work, and X, Y and Scale are all the compositor carries. Rejected: a `CompositorScene` drawing the blobs (they would stop following `Motion.State`, which only reaches controls).
- **Glass needs the moving backdrop.** Panels and stats cards use a translucent fill (not element `Opacity`, so content stays opaque), a 1 px top-lit border and a soft shadow. Reason: translucency over a flat fill is invisible, so the glass comes with the drifting blobs.
- **The window asks for Mica, then AcrylicBlur, and paints its own base.** `MainWindow` hints `Mica, AcrylicBlur, None`, the window style clears Semi's `WindowDefaultBackground` to transparent, and the shell's root grid paints a 90% `#121318` base under the blobs (the intro paints its own opaque background). Outcome of the "Window material on Semi" question: Windows 11 grants Mica (`ActualTransparencyLevel` reads `Mica`), which tints faintly through the base; where the hint is refused the base composites over black, a difference of a few RGB levels, so the look is the same. Reason: an opaque base would hide the material entirely, a fully transparent one would leave the blobs over black or the wallpaper.
- **Reduced motion is a first-class setting.** System (the default) follows the OS through `FollowSystemReducedMotion`; Full and Reduced set the flag, applied at startup before the window exists and live on every change. Reduced, motion becomes fades, loops stop and the burst is skipped, but the colors still change. Reason: the project-wide rule (§4) applies to apps too.
- **MVVM with CommunityToolkit.Mvvm**, compiled bindings and `ObservableCollection` task lists, so `Reorder` needs no command. Reason: the idiomatic Avalonia stack, already centrally managed.
- **No assets beyond fonts.** Icons are `PathGeometry` resources. Reason: no licensing questions, and morphable icons need paths anyway.
- **The pages swap in a `TransitioningContentControl`, not a `Carousel`.** Focus and Stats, plus Tasks in compact, swap in one `PageHost` with `TempoMotion.PageSwap` (`PageSharedAxis` along X) in both arrangements, its direction from `MainViewModel.IsBack` by the bottom bar's order, Tasks < Focus < Stats. Going back plays an explicit mirrored pair (`BackEnter`/`BackExit`) rather than the forward pair reversed, so the back motion eases out too. Reason: a carousel only hides the view it is not showing, so the stats bars' `Presence.Arrive` stagger would never replay; a fresh view per swap does. Because each view is rebuilt, `FocusView` assigns the play icon's `IconToPause` states from `OnLoaded` (attaching while a `MorphTo` state holds throws).
- **A task moving to Done waits `MainViewModel.DoneMoveDelay` (450 ms).** Reason: the move is a removal and an add across two lists, and the new row's `Follow` snaps, so the strike line must draw in the old row first.
- **Seeding is first-run only, plus an explicit restore.** When `tempo.json` does not exist (`TempoStore.Exists`), `MainViewModel.LoadAsync` loads `SampleData` and saves it at once; an existing file never seeds, even an empty one, and a corrupt one still starts empty. `RestoreSampleData` and `ClearAll` replace the tasks and the session log in place (settings stay) and abandon a running segment first, so it never logs against a task that is gone. Reason: a showcase must look alive on first launch, but a user who clears it must stay cleared, and restore keeps the demo one click away. Rejected: a `--demo` flag (nobody finds it) and seeding whenever the list is empty (fights Clear all).
- **Sample data is deterministic and relative to today.** A fixed `Random` seed builds sixteen tasks and eight weeks of history (weekdays heavier, a few gap days, a nine-day streak through earlier today), dated back from the current local day, with every record before now. Reason: screenshots and tests stay stable, and the streak is always current.
- **Tags are in the model.** `TaskItem.Tag` is an optional `TaskTag`, a fixed set of five (Writing, Code, Design, Admin, Personal) with colors in `TempoMotion.TagBrush`; files from before it load with no tag. Reason: filtering and the time-by-tag donut need a category, and a fixed set needs no tag editor. Rejected: free-form tags (editing UI and color assignment).
- **Tags filter through a second collection.** The open list binds `MainViewModel.VisibleTasks`, which follows `Tasks` and `TagFilter` by removing, then inserting, only the rows whose visibility changed, never a Reset, so the rows that stay reflow (`Animate.ItemLayout`) while the others leave and arrive with `RowExit`/`RowEnter`. A task leaving it while selected is deselected, and a task added under a filter takes the filter's tag so it stays in view. Reason: a filtered view (`DataGridCollectionView`-style) or a rebuilt list resets the `ItemsControl`, which neither reflows nor runs presence. Rejected: hiding filtered rows with `IsVisible`, which leaves the indicator and reorder indices counting hidden rows.
- **Reorder stays on under a filter.** A move in `VisibleTasks` (what `Reorder` makes) is replayed in `Tasks`, placing the task just before its new visible successor, or after its predecessor when it lands last, so the hidden tasks keep their places. Reason: disabling reorder while a chip is chosen would be a mode nobody expects, and the mapping is one `Move`. Done is not filtered: it is a collapsed history, and the chips sit with the open list.
- **The whole row is the drag target, held first on touch.** The task rows have no grip: a mouse drags any row at once past Reorder's 3 DIP threshold, and a touch must hold still for 400 ms (`Reorder.TouchHold`) before the row lifts, so a vertical touch scrolls the list and a horizontal one reaches the swipe actions; a hold let go without moving opens the row's details (`Reorder.HoldCommand` bound to `OpenDetailCommand`), so one long press either reorders or opens, decided by whether the finger moves. Reason: a grip beside the checkbox made misses inevitable on a phone, and the gallery's reorder demos drag the whole item. Rejected: keeping the grip as a mouse-only affordance, which still costs a column.
- **Compact rows open their details from a "⋯" button.** Each row shows a 32 px `Button.row-more` at its right edge under `compact` (hidden wide), running `OpenDetailCommand` for its task; double-click still opens details with a mouse. Reason: a touch row already swipes both ways, reorders on a hold and checks, so a double tap (or a single tap, tried first) competed with those gestures and rarely landed. Rejected: a single tap on the row, which also fired when a touch meant to close a swiped row or begin a hold.
- **Swipes commit or spring back, never pin.** The task rows set `Swipe.Reveal` false: the complete and delete actions show under a drag, a full swipe past half the row runs them, and anything shorter coasts closed; a context request still opens them. Reason: on touch a small sideways drift pinned a row open on its actions, and closing it took another gesture.
- **The chips are `ListBox`es over `object` lists** (`MainViewModel.TagFilters`, `TaskItemViewModel.TagChoices`: a label, then the five tags) with their `SelectedIndex` bound to an index view of the nullable tag (`TagFilterIndex`, `TagIndex`). Reason: a `ListBox` cannot select a null item, and an "All"/"None" chip is what a null tag means; `TempoMotion.TagBrush` colors whichever item is a tag. The chip row's `Selection.Indicator` glides with `RowSelect`, like the task rows and the view switch.
- **Stats is two rows below the totals wide, one column compact, in a `ScrollViewer`.** Wide, the 7-day bars and the time-by-tag donut share a row, the 12-week heatmap and the best-day line take the next, and the bars are 120 px tall; compact lists the totals a row each, stacks the cards, puts the legend under the donut and shrinks the heatmap to the card's width. Reason: two rows fit the default 1100×720 window and the donut's legend needs half the panel's width, but a shorter window (960×640) clipped the page, and a phone width has room for one card across.
- **Scrollers cue their edges.** A page's scroller (the task list, Stats) reaches out to the window edge (`edge-scroll`), so its overlay scrollbar sits in the shell's gutter, not inside the card, with the page host and the views unclipped. The task list, the Done list and Stats fade a card-wide shadow in at an edge with more beyond it, ramped by the distance left to scroll (`Views/ScrollEdge.cs`), and the compact chip row hides its scrollbar and fades its ends instead. Reason: the cards cut content off at a hard line, and a ramp tracks the scroll without a timed animation. Rejected: an opacity mask on the lists, which fades the rows themselves rather than reading as content passing under a header.
- **Every scroller eases the wheel.** One `ScrollViewer` style sets `Scroll.Smooth`, so the task lists, Stats and the chip rows (template parts included) glide a notch at a time on Windows; touchpads, touch, scrollbars and keys pass through, and reduced motion keeps native steps (BRIDGE-SCROLL). Reason: native notches jump 50 DIPs at once, which reads as stutter next to the app's motion.
- **A narrow task list puts the tag and sessions under the title.** A container query on the `TasksView` width (`max-width:399`) moves the row's `task-meta` to a second line, which covers the 340 DIP column and phone widths. Reason: on one line the tag pill and up to six dots left the title a few characters. Rejected: keying it to `compact`, which misses the wide layout's column.
- **The heatmap is Monday-first columns of weeks, ending at today.** `StatsViewModel.Heatmap` runs from the Monday eleven weeks before this one through today, so the days after today are absent rather than blank and today's cell is the last; shades step at 1, 30, 60 and 120 minutes. It reveals outward from today by each cell's `HeatmapCell.Distance` (a `FunctionValue` delay in `TempoMotion.HeatCellArrive`). Reason: an arrival batch sees only the arrivals so far as its targets (BRIDGE-PRESENCE-022), so `Presto.Stagger` with `Grid` and `From = Last` measured every cell from itself. Rejected: blank future cells, which make "last" not today.
- **The donut is stacked full circles, each following one number.** `StatsViewModel.Segments` (the five tags, then Untagged) are the same `DonutSegment` instances on every recompute, and each `Ellipse` follows its `End` with `Follow.Draw` (timed by `TempoMotion.DonutMorph`): the share of its tag plus those after it, drawn from the top under the later segments, so each shows only its own arc and a range change eases every arc at once. `TempoMotion.DonutDraw` sweeps them in from `0 0` on arrival. Reason: `Follow.Draw` follows only a `0 p` slice, and `Animate.OnChanged` reverts its animation when it completes (BRIDGE-ATTACH-018), which would restore the full stroke. Rejected: one arc per segment with a start–end `Draw` slice, which needs both triggers.
- **Time by tag reads each task's current tag.** `MainViewModel` hands `StatsViewModel` a lookup over the open and done tasks and calls `RefreshTags` when a tag or either list changes; focus on no task or on a deleted task counts as Untagged, and Week is the last 7 days. Reason: the log stores only task ids, and retagging a task should move its history with it.
- **Plain-key shortcuts (Space, N, Del) are off while a text box has focus.** Reason: Avalonia runs window key bindings before the focused control sees the key, so typing would start the timer or delete a task.
- **`tests/Tempo.Tests` runs headlessly on Semi's Dark theme and Tempo's styles**, without Tempo's `App`, with each window test in both motion modes; `MainWindowTests` runs the intro, handoff, tasks and a mode change end to end, and from the first-run sample data a tag filter, a session, a Stats visit, a clear and a restore, each at 1100×720 and at 360×780 (navigating by the switch or the bottom bar). Reason: as for the gallery, DevTools cannot send drags or key shortcuts, and `App` attaches the developer tools, which refuse a second attachment in one process.
